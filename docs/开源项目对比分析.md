# 开源记账项目调研与对比分析

> 调研日期：2026-09-03。数据（Star 数、最近推送、许可证）来自 GitHub API 实时查询，检索方式为多组关键词的 Repository Search（`记账` / `账本` / `bookkeeping` / `expense tracker` / `money manager` / `personal finance ledger` / `budget app` 等），并逐一核对了候选项目 README 的功能清单。

## 一、需求定义

目标产品：**移动端响应式 Web 记账本**，包含三大模块：

| 模块 | 关键需求点 |
|---|---|
| 账本 | 可创建多个账本；账本间数据独立；按账本记录收支 |
| 资产 | 总资产、净资产（资产 − 负债）；每笔收支记录汇总 |
| 统计 | 按周 / 月 / 年统计；支出 / 收入 / 结余统计图；净资产趋势图 |

附加期望：响应式布局（手机 + 桌面）、轻量易部署、可自主可控的数据。

## 三、关键结论

**没有一个现存项目能完整覆盖全部需求。** 差距集中在三种情况：

1. **功能全但是 App，不是响应式 Web**：BeeCount（多账本/多账户/图表/年度报告最完整）、Cashew 都是 Flutter 应用；Web 端要么依赖自建云服务，要么体验降级。
2. **是 Web 但缺「多账本」或「净资产」**：ezbookkeeping 移动端体验最好（官方明确"为移动和桌面提供定制界面 + PWA"）但单账本；cashbook 有多账本 + 移动适配但已宣布停更且缺资产模块；actual / ExpenseOwl 单账本、无净资产概念。
3. **资产与报表强但太重**：firefly-iii（PHP + MySQL + Redis）、maybe（已归档）、paisa（需要维护 ledger/beancount 数据文件）功能强大，但对「个人轻量记账」来说部署与使用成本过高。

## 四、重点候选点评

### 4.1 mayswind/ezbookkeeping — 移动端体验标杆（5.5k★，MIT，Go+Vue3）
- 亮点：**同一套服务为移动与桌面提供定制界面**、PWA、多币种、单二进制极简部署；活跃度极高（当天仍有提交）。
- 缺口：单账本（按用户隔离），无独立「资产/净资产」模块，统计为常规分类/趋势图。
- **借鉴**：移动优先的交互形态（底部导航、悬浮记账键）、轻量化部署理念、PWA 定位。

### 4.2 TNT-Likely/BeeCount — 功能最接近但形态不同（2.3k★，Flutter）
- 亮点：**多账本（每本独立币种）/ 多账户 / 二级分类 / 周期记账 / 图表分析 / 年度报告**一应俱全，本地优先 + 5 种自选云同步；需求描述里的「生活/工作分开记账」正是它的典型用法。
- 缺口：Flutter App 形态；许可证为 BSL（Business Source License，非 OSI 开源，商用受限），代码不能直接作为 MIT/Apache 基础复用。
- **借鉴**：数据模型（账本→账户→分类→流水四层）、「账本/资产/统计」三栏信息架构、本地优先原则。

### 4.3 dingdangdog/cashbook — Web 多账本的最直接参照（382★，Nuxt3）
- 亮点：明确实现「**多账本模式，账本之间数据独立**」「共享账本」「WEB 移动端适配」，图表清单完整（支出类型/支付方式饼图、每日曲线、每月柱状、消费日历），支持支付宝/微信/京东 CSV 导入。
- 缺口：作者已声明**不再加新功能、随时停更**（迁移新仓库 Jimily）；需要 Postgres 等数据库；无资产/净资产模块。
- **借鉴**：多账本交互（胶囊切换 + 管理面板）、统计页图表选型（ECharts 饼图 + 柱状 + 曲线组合）。

### 4.4 getmoneynote/moneynote — 需求匹配度高但工程重（1.4k★，Java 全家桶）
- 亮点：功能清单几乎逐条命中——「监控个人**资产负债**、记录支出收入、**支持多个账本记账**、多币种、报表统计、Docker 一键部署」。
- 缺口：Spring Boot 后端 + Antd Pro 网页端 + Flutter App 三仓库组成；PC 优先，移动端 Web 体验一般；更新平缓。
- **借鉴**：「资产 + 多账本 + 报表」的模块划分本身就是本项目的三模块蓝本。

### 4.5 firefly-iii / actual / paisa — 资产与报表的老师（合计 56k★）
- firefly-iii：资产账户 + 负债 + 净资产仪表盘 + 预算 + 报表的概念体系最完整，是「资产模块」设计的主要参考；但 PHP 技术栈与部署重量超出个人轻量场景。
- actual：本地优先 + MIT + React 的工程范式值得学习；信封预算理念与「多账本记账」不同。
- paisa：净资产趋势与图表呈现漂亮，但需要 ledger 数据文件，录入型记账体验弱。

## 五、需求 → 设计决策映射

| 本项目需求 | 决策 | 站在谁的肩膀上 |
|---|---|---|
| 多账本、账本间数据独立 | 账本(Book)为顶层维度，流水挂账本；胶囊切换 + 管理弹窗 | cashbook、BeeCount、MoneyNote |
| 总资产 / 净资产 | 资产/负债两类账户，净资产 = Σ资产 − Σ负债，实时联动流水 | firefly-iii、paisa、MoneyNote |
| 每笔收支记录 | 跨账本汇总流水列表，带账本标记与收入/支出筛选 | ezbookkeeping 的流水形态 |
| 周/月/年统计 + 结余 | 周期分段桶（周按日/月按日/年按月），双柱 + 结余折线 | cashbook、ezbookkeeping |
| 支出/收入构成图 | 环形图 Top 分类 + 其他，移动端图例底部滚动 | ExpenseOwl、cashbook |
| 净资产趋势图 | 近 12 个月逐月末净值面积图 | paisa、firefly-iii |
| 移动端响应式 | <820px 底部 TabBar + FAB / ≥820px 侧边栏；safe-area 适配 | ezbookkeeping 的双端定制思路 |
| 轻量零部署 | 纯前端 SPA，zustand persist → localStorage，JSON 导入导出 | actual 的本地优先、BeeCount 的数据主权 |
| 可持续复用 | 全新 MIT 许可实现，未复制任何候选代码 | — |

## 六、为什么不直接二次开发某个候选？

- **ezbookkeeping / cashbook**：加「多账本 + 净资产」等于动数据模型核心，Go/Vue（或 Nuxt+Prisma+数据库）的全栈改造与维护成本，高于写一个零后端的纯前端实现；且 cashbook 已停更、ezbookkeeping 上游演进快，fork 后长期合并冲突压力大。
- **BeeCount / Cashew**：Flutter 形态不符「响应式 Web」诉求；BeeCount 的 BSL 许可证也不允许直接复用代码。
- **firefly-iii / MoneyNote**：功能覆盖但部署/维护重量与「个人轻量记账」矛盾。
- 因此选择：**以调研结论为设计输入，从零实现一个 MIT 许可、纯前端、移动优先的最小完备产品**，即本仓库 `pocket-ledger`。
